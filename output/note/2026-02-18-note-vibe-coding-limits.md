# 「Vibe Codingの限界」から見える仕様駆動開発の復権

数ヶ月前、エンジニアの間で話題になった「Vibe Coding」。自然言語でAIにコードを書かせるこの手法は、まるで魔法のように思えた。

しかし今、現場からは苦い声が上がり始めている。"Vibe"だけでは乗り切れない、根本的な問題が浮上している。

## 1. Red Hatが警鐘を鳴らす「3ヶ月後の真実」

エンタープライズ向けLinuxを手がけるRed HatのCTOが先日、注意喚起を出した。Vibe Codingのコードは、3ヶ月後には「唯一の真実」になってしまうという。

つまり、なぜその設計を選んだのか、どんな前提で書かれたのか、誰にも説明できなくなるということだ。

セキュリティ脆弱性が2.74倍になるという研究結果もあったが、今度は保守性の危機だ。動くコードは増えるが、**修正や改善のための文脈が失われていく**。

この問題は、日本の開発現場にとって特に痛い。丁寧な設計と手順を重んじる開発文化の中で、説明責任のないコードは受け入れられない。

## 2. SoftBank 250万Agentの教訓——導入と効果のギャップ

別の示唆に富む事例もある。SoftBankが社内に展開した250万個のAI Agentだ。

数字だけ見れば圧倒的だ。しかし、これが反面教師となっている。「導入した」だけでは効果が出ないという現実が見えてきた。

現場の開発者の間では、こうした声が聞こえる。"Agentを増やしても、ワークフローが変わらなければ、ただの作業の重複になる"。

これは重要な示唆を与えてくれる。AIツールの価値は、ツール自体の性能ではなく、**どう組み込むか、どう設計するか**にかかっている。

## 3. 仕様駆動開発の復権——なぜ今、仕様が重要になったのか

そこで注目を集めているのが、spec-driven development（仕様駆動開発）だ。

Vibe Codingの問題は、仕様がコードの中に埋没してしまうことにある。人間が読める設計意図が失われ、バグ修正や機能追加のたびにAIに再度「感覚で」頼らなければならなくなる。

仕様駆動開発はこの流れを逆転する。まず人間が仕様を書き、それをAIが実装する。コードは常に仕様という「文脈」を持つ。

BoxのCEO、Aaron Levieも指摘する。AgentのROIはモデルの強さではなく、**ワークフローの再設計**に依存するという。

ここに日本の開発者にとって親しみやすい価値観がある。ものづくりにおいて、設計と手順を大切にするという、日本的な開発文化と合致している。

## 4. 日本の開発者にとっての示唆

こうした動きは、日本の開発現場にどう活かせるだろうか。

まず、品質と保守性への意識の高さは強みだ。セキュリティと同様に、保守性も「後から考える」ものではなく、設計段階から組み込むべき品質属性だ。

次に、仕様書文化の活用だ。日本の開発組織には、仕様を残し、レビューを重ねる伝統がある。これをAI時代にアップデートすれば、Vibe Codingの落とし穴を避けられる。

ただし、注意点もある。仕様駆動は、仕様を書く作業を増やすわけではない。AIに明確な指示を出すための「最小限の文脈」であり、過剰なドキュメント化は避けるべきだ。

## 品質と速度の新しいバランス

Vibe Codingは間違いなく生産性を上げた。しかし、それがもたらしたのは、速度と品質のトレードオフではない。新しい問いだ——**どこまでをAIに任せ、どこを人間が設計するか**。

仕様駆動開発の復権は、決して古い手法の復活ではない。AI時代にこそ意味を持つ、品質と説明責任を確保するための新しいアプローチだ。

日本の開発者にとって、これは追い風となるはずだ。ものづくりの丁寧さを活かしつつ、AIの生産性も享受できるバランスを見つけられるからだ。

コードを書く速度が上がった今、私たちが問われているのは、**何を作り、なぜ作るか**を明確に保つ力だ。仕様があるからこそ、AIは単なるコード生成器ではなく、意図を実現するパートナーになれる。
