# 我把500万条数据库记录「拆散」了——为什么 AI 读不懂好好的数据库

上周我做了一个让团队困惑了一会儿的决定：把 GBaseGTM 数据库里的500万家日本企业，每一家都变成一个独立的文本文件。

不是导出备份，不是数据迁移。是真的把一个结构化数据库，拆成500万个 Markdown 文件。

工程师同事问我：好好的数据库不用，为什么要这么折腾？

我想了想，说：**因为 AI 读不懂数据库。**

---

## 数据库是给机器看的，不是给 AI 看的

这是我做 GBaseGTM 一年多之后才真正想清楚的一件事。

我们一直说 GBaseGTM 是一个 AI 销售平台。但说实话，很长一段时间里，AI 在我们产品里扮演的角色更像一个翻译：用户输入自然语言，AI 把它翻译成数据库查询，然后返回结果。

AI 并没有真正「理解」那500万家企业。它只是在帮你找。

举个具体的例子。我们数据库里有一家公司叫「株式会社山田商事」，存的是：

```
公司名：株式会社山田商事
法人番号：1234567890123
地址：东京都中央区...
行业：批发业
员工数：45
官网：yamada-shoji.co.jp
```

这对数据库来说是完美的。可以精确查询、快速索引、高效存储。

但如果你想让 AI 真正理解这家公司——它在做什么业务、最近有什么动向、跟你的产品有没有合作空间——它需要的是完全不同的东西。它需要读这家公司的官网、新闻、招聘信息，然后形成一个「对这家公司的认知」。

**数据库给的是字段，AI 需要的是理解。**

这是两种完全不同的信息形态。我们花了一年时间做了一个很好用的数据库产品，但下一步要做的事——让 GTM Agent 真正主动帮用户找商机——需要的不是一个更好的数据库，而是一个 AI 能读懂的知识库。

---

## 一家企业，一个文件

我最终确定的方案是：每家企业对应一个 Markdown 文件。

文件名用唯一 ID 命名，格式是「法人番号-公司名-地址」。

为什么是法人番号？因为日本企业有一个很头疼的问题——同名。全日本可能有几十家公司都叫「山田商事」。你光靠公司名根本分不清谁是谁。

法人番号是日本政府给每家合法企业颁发的唯一编号，相当于企业的「身份证号」。从国税厅的权威数据库拿到这个号，基本就锁定了这家公司的真实身份，不管它叫什么名字。

这一步看起来是技术细节，但对我来说是产品决策：**用最权威的数据源作为企业身份的锚点**，后面所有的数据爬取和信息补充，都围绕这个锚点展开。

文件里装的不是数据库字段，而是这家公司的「档案」：官网内容、公司简介、主营业务、联系方式、近期动态。格式是人能读、AI 也能读的 Markdown。

同时，这个文件和数据库双向同步——文件更新，数据库也跟着更新。这样查询效率还在，但 AI 现在也可以直接读文件，真正「读懂」一家公司。

---

## 三个 Skill，各干各的

光有文件结构还不够。500万家企业的数据不可能手工维护，需要 Agent 来跑。

我们设计了三个 Skill，并行运转：

**爬虫 Skill**：负责获取数据。按照模板格式，持续爬取每家企业的官网、新闻、招聘信息，填充到对应的文件里。碰到同名公司，靠法人番号加地址信息做交叉验证，确认是哪一家。这个 Skill 是我在负责设计。

**搜索 Skill**：负责理解数据。用户查询的时候，不只是匹配关键词，而是从 MD 文件里提取语义，找到真正相关的公司。另外，当某家公司的文件更新后，把变更同步写回数据库，保持一致性。这块是王重明在做。

**触达 Skill**：负责使用数据。当用户选定目标企业，AI 读取这家公司的档案，生成个性化的触达内容，自动填写表单或发送邮件。真正的个性化，不是模板填空，是读懂这家公司之后写的。金老师负责这块。

三个 Skill 各自跑 loop，互不干扰，但共享同一套文件体系。**爬虫负责写，搜索负责读和更新，触达负责用。**

我不会写代码，但我能想清楚这三件事之间的关系。这个架构，是我画在纸上的。

---

## 这不只是技术重构

做这件事的时候，有个更大的图景在我脑子里。

GBaseGTM 现在能做的是：用户找企业，AI 帮你找得更准更快。

我们想做到的是：用户告诉 AI 自己的产品是什么，AI 主动去找商机，发现哪家公司最近在招聘销售、刚完成融资、正在扩张——然后主动推送给用户说「这家公司现在可能需要你的产品」。

前者是工具，后者是助手。

工具需要的是一个好数据库。助手需要的是对每家企业真正的理解。

**把500万条记录变成500万个文件，就是在为这个助手做准备。**

---

## 非工程师也可以设计 Agent 架构

最后说一件对我来说比较重要的事。

我是产品设计师出身，不懂代码。这次重构的架构设计——文件格式、唯一 ID 的逻辑、三个 Skill 的分工——都是我想的，不是工程师给的方案。

说实话，一开始我对这件事有点虚。感觉「架构设计」是工程师的领域，轮不到我来定。

但后来我发现，这种虚是多余的。**设计 Agent 架构，本质上和设计产品功能没什么区别**：想清楚用户（或者下游的 Agent）需要什么输入，产出什么，中间怎么协作。这是产品思维，不是工程思维。

我现在用 Claude Code 来做产品，不写代码。但我越来越觉得，真正决定 AI 产品好不好用的，往往不是代码写得有多好，而是有没有人想清楚「这件事应该怎么组织」。

如果你也是非工程师背景，正在考虑怎么做 AI 产品——我觉得这个问题值得认真想一想：**你的数据，是给机器查询的，还是给 AI 理解的？**

这两件事，差得很远。
