# 从 Vibe Coding 到规范先行：AI 产品开发的第二个周期

去年这个时候，我还在朋友圈晒"3 小时用 Claude 做完一个 Chrome 插件"的截图。

那时候的感觉是：不需要懂代码，只要会描述需求，AI 就能帮你把东西做出来。这种 Vibe Coding 的快感，像拿到了一把万能钥匙。

但上周 Red Hat 发布的一份内部报告，让我冷静了下来。

## Vibe Coding 的狂欢与冷水

Red Hat 工程团队追踪了 47 个用 AI 辅助开发的项目。6 个月后，他们发现了一个规律：

**前 3 周，Vibe Coding 速度是传统开发的 3-4 倍。**

**但 3 个月后，这些项目遇到了一个共同的问题：没人能解释代码为什么要这样写。**

更麻烦的是后续数据：

- 安全漏洞数量是人工编写代码的 **2.74 倍**
- 代码可维护性评分平均下降 **40%**
- 当最初的需求者离开项目后，新接手的开发者需要 **2-3 倍** 的时间才能理解代码逻辑

Red Hat 给这种现象起了个名字：**"唯一真相陷阱"**。

代码成了唯一的文档，而生成这段代码的决策过程——为什么选择这种方案、放弃了哪些替代方案、边界条件是什么——都消失在了 AI 的黑箱里。

这不是在说 AI 写代码不好。而是在说：**当我们只关注"写出来"，而不关注"为什么这样写"时，我们在积累技术债务。**

## 为什么 Vibe Coding 会触壁

Vibe Coding 的本质是什么？

是把"写代码"这个动作，从需要多年训练的专业技能，变成了一个自然语言交互的过程。

这个改变在原型阶段非常有效。因为原型阶段的核心目标是**验证假设**，而不是**构建系统**。

但当产品进入生产环境，游戏规则变了。

生产环境要求：
- 可追溯的决策记录
- 可维护的代码结构
- 可协作的知识传递
- 可审计的安全合规

而 Vibe Coding 在快速生成代码的同时，恰好省略了这些"不重要"的东西。

这就是为什么 Red Hat 观察到的拐点发生在 3 个月左右——那正是原型验证完成、准备进入生产迭代的节点。

## Spec-driven：不是回归瀑布，是新的工作方式

面对这个问题，业界的解法不是回到传统的瀑布式开发，而是**Spec-driven Development（规范驱动开发）**。

Spec-driven 的核心逻辑是：**在让 AI 写代码之前，先把"要解决什么问题、为什么这样解决、边界条件是什么"写清楚。**

听起来像是常识？但和 Vibe Coding 的最大区别在于：

**Vibe Coding 的流程是：想法 → AI 生成代码 → 运行看效果 → 迭代**

**Spec-driven 的流程是：问题 → 约束条件 → 方案比较 → 决策记录 → AI 生成代码 → 验证**

多了几步，但换来的是：
- 每一个技术决策都有可追溯的理由
- AI 生成的代码有明确的上下文边界
- 其他人（包括未来的自己）可以理解这段代码为什么存在

这周我做的 PM-Quill 工具，其实就是这个思路的产物。

它不是在帮你写代码，而是在帮你**写代码之前**把问题定义清楚。

设计初衷很简单：既然 AI 可以让"写"变得廉价，那么"写什么"和"为什么写"就变得值钱。

## SaaS 替代的实战化

说回简报里的另一个数据点。

Greg Isenberg 最近预测：**未来 3 年，50% 的 SaaS 产品会消失，被零员工 Agent 集群替代。**

他的计算逻辑是：一个 18 个月前还不存在的 Agent 团队，现在已经能做到年营收 $1 亿，而成本结构是传统 SaaS 公司的 1/20。

这个数字听起来很夸张，但拆解一下就会发现它的合理性。

传统 SaaS 公司的成本结构：
- 70% 人力（工程师、销售、客户成功）
- 15% 基础设施
- 10% 营销
- 5% 其他

Agent 集群的成本结构：
- 90% 算力
- 8% 基础设施
- 2% 其他

这不是功能的替代，是**成本结构的替代**。

当 AI Agent 可以处理客户支持、代码维护、甚至产品迭代时，传统 SaaS 的"软件即服务"模式，就变成了"智能即服务"。

但这个转变有个前提条件：**你必须把工作流重新设计一遍。**

Aaron Levie（Box CEO）在最近的一次访谈中说了一句话，我印象很深：

**"Agent 的 ROI 不取决于你买了什么工具，而取决于你重新设计了多少工作流。"**

这跟 Spec-driven 是一个逻辑——工具是廉价的，设计是值钱的。

## 中国 AI 祛魅：从红包大战看叙事转向

最后说说国内的情况。

36氪上周末发了篇文章，标题叫《祛魅时刻》。里面提到一个细节：

字节、阿里、腾讯、百度春节一共发了 **45 亿红包**，但目的不是为了拉新，是为了教用户"怎么跟 AI 对话"。

也就是 prompt engineering。

这个信号很有意思。

去年这个时候，大厂们还在比谁的模型参数更大、谁的 benchmark 分数更高。现在，它们开始教用户"怎么用"了。

这说明什么？

**中国 AI 市场正在从"叙事竞争"转向"留存竞争"。**

叙事竞争的阶段，比的是谁能讲出更好的故事——更大的模型、更酷的功能、更科幻的应用场景。

留存竞争的阶段，比的是谁能帮用户解决实际问题——更稳定的输出、更低的学习成本、更明确的使用场景。

字节最近的动作很能说明问题：豆包（对话）、Seedance（视频）、SeedChip（硬件）三线并进，但核心逻辑都一样——**让用户真正用起来的产品**。

而不是让用户觉得"好厉害"的产品。

## 作为 Builder，我在这个周期里的位置

说了这么多，回到我自己。

去年我在做 Vibe Coding，今年我在做 Spec-driven。

不是因为 Vibe Coding 错了，而是因为我所处的阶段变了。

从"验证想法"到"构建产品"，从"个人项目"到"可协作的系统"，需要不同的工作方式。

PM-Quill 是我在这个转变中的一个尝试。它解决的是我自己的痛点：当 AI 可以瞬间生成代码时，我发现自己经常在"想做什么"和"实际做了什么"之间迷失。

Spec-driven 不是让开发变慢，而是让**正确的决策**有机会发生。

SaaS 替代也好，Agent 平台化也好，中国 AI 祛魅也好，底层的逻辑是一样的：

**当技术门槛被拉平，设计问题的能力就成为新的护城河。**

这不是说工程师不重要了。恰恰相反，工程师的价值正在从"写代码"转移到"定义问题"和"设计工作流"。

如果你也是 Builder，我想分享一个最近在用的判断标准：

**当你用 AI 做完一个功能后，问自己：三个月后的我，还能理解今天为什么这样设计吗？**

如果答案是不确定，那可能需要停下来，把 spec 补一补。

毕竟，Vibe Coding 让我们能更快地造东西。但 Spec-driven 让我们能**持续地**造东西。

而持续，才是 Builder 的终极能力。
